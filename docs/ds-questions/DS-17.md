## 1. Нет ключей шаблонов `request_created` / `request_cancelled` → notify на создание и отмену не отправляется вообще

**Что неясно.** Тикет DS-17 (формулировка от координатора) требует «notify студенту (category
request, ключ request_created если есть)» при создании и «notify (ключ request_cancelled если
есть)» при отмене. В `src/server/notify-templates.ts` (NOTIFY_KEYS) таких ключей нет; писать
тексты уведомлений DeepSeek не имеет права (DEEPSEEK-TASKS §3 п.11, файл ведёт Claude).

**Принятое решение.** `notify()` на создание, отмену и прямое сообщение студента не вызывается.
Обоснование:

- событие студент и так породил сам — уведомление «вы подали заявку» избыточно;
- добавлять ключи в `notify-templates.ts` не имею права (запрещённый файл, тексты для людей);
- SPEC §6.6 не описывает уведомление о собственной подаче заявки.

**Варианты для решения.**

1. Оставить как есть (уведомления только о действиях сотрудников: taken / needs_info / ready /
   issued / rejected) — текущее поведение.
2. Добавить ключ `request_created` (класс personal, категория request) и вызвать в
   `createRequestRow` после вставки.
3. Решить, нужно ли вообще уведомление при отмене — по сути студент сам отменил.

## 2. payload у data_fix не совпадает с formSchema типа data_fix

**Что неясно.** В тикете сказано: `fields = { field, comment }`, при этом formSchema типа
`data_fix` (db/seed/request-types.ts) описывает поля `field` (select с русскими вариантами
«ФИО/группа/…») и `correctValue` — то есть ключ `comment` не входит в схему, а значения
`fullName`/`contacts` не входят в options. Форма data_fix в UI, похоже, bespoke (контракт
`DataFixBody`), поэтому формально валидировать payload по formSchema тип `data_fix` не должен.

**Принятое решение (первый вариант).** payload сохраняется как `{ field: 'fullName'|…,
comment: '…' }` — машинные значения из контракта, без валидации по formSchema.

**Риск.** Карточка заявки (RequestDetailDTO.fields) рендерится UI по formSchema — ключей
`comment` в схеме нет: отображение полей data_fix в карточке надо учесть в UI (Claude).
Если правильнее было хранить `{ field: 'ФИО', correctValue: '…' }` (машинный код → подпись сида)
— нужен маппинг и решение контракта; тогда я поправлю `createDataFixRequest`.

## 3. На сколько путей распространять квоту 10 заявок в час

Тикет DS-17 задаёт лимит только для `POST /api/me/requests`. Решено: квоту расходуют все три
пути создания заявок (`create`, `resubmit`, `data-fix`) — все создают новые заявки и имеют одну
и ту же вектор атаки. Если лимит должен применяться только к одному эндпоинту — скажите,
вынесу вызов `consumeStudentQuota` из `resubmitMyRequest`/`createDataFixRequest`.

## 4. Мелочи

- `POST /api/me/requests/:id/messages` и `/cancel` не обёрнуты в `withIdempotency`: в тикете
  idempotency упомянут только для создания и повторной подачи («свой Idempotency-Key»).
  Если нужно для всех POST — пришлите подтверждение, добавлю.
- Сообщение студента обновляет `updatedAt` и `studentSeenAt` заявки (студент действовал
  последним, точка «unseen» не появляется). Смысл: `updatedAt` — «время последнего события
  заявки». Если по SPEC студенческое сообщение не должно двигать `updatedAt` (меняется только
  статус) — однострочная правка в `addRequestMessageForStudent`.
