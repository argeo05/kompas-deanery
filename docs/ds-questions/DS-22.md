# DS-22 — Календарь ICS: решения по url и хранению токена

Не блокирующие решения приняты субагентом DS-22 (реализация выполнена, тесты написаны,
vitest/db-команды не запускались по ограничению сессии — проверка остаётся за координатором).

## 1. url — относительный, origin подставляет интерфейс

`IcsUrlDTO.url` — путь `/api/ics/<token>.ics` **без origin**. В оригинальном вопросе тикета
origin предлагалось брать из `req`, но детерминизм ответа важнее: BETTER_AUTH_URL,
заголовки прокси и rewrites могут отличаться от фактического хоста клиента, а у
календарных подписок url живёт годами. Клиентский экран знает свой origin и склеивает
абсолютную ссылку для display/copy (классический паттерн; origin не секрет).

## 2. Токен и хеш

- Токен: `randomBytes(32)` → `base64url` (43 символа, url-безопасный, 256 бит).
- В `ics_tokens` — только `SHA-256` (hex), поиск публичным роутом — по `token_hash` (uniq).

## 3. Проблема «повторный GET возвращает ту же url» при hash-only хранении

По SPEC §6.9 и тикету в БД хранится только SHA-256, значит из строки БД токен не
восстановить — повторный показ той же ссылки невозможен без дополнительного хранилища.
Схему менять нельзя (Migration/schema — зона Claude), поэтому сырой токен кэшируется в
существующей таблице `idempotency_keys`:

- строка `(user_id, key = "ics-feed-url")`, `requestHash = sha256("GET /api/me/ics")`,
  `response = { "token": "<сырой токен>" }`, `statusCode = 200`;
- запись и хеш токена пишутся **в одной транзакции** `withUserTx` (атомарно, консистентны);
- `getMyIcsUrl` возвращает ссылку из кэша, только если `sha256(токен из кэша) === token_hash`:
  расхождение означает потерю кэша (ежедневный сброс демо-данных, правка руками) — тогда
  тихо создаётся новый токен (rotate);
- `rotate` перезаписывает обе строки, старый токен находимым не остаётся → 404;
- таблица `idempotency_keys` личная (RLS `idempotency_keys_own`), сырой токен виден
  только самому студенту/владельцу БД.

**Вопросы к Claude (найти при ревью):**

1. Считать ли кэш в `idempotency_keys` приемлемым постоянным решением, или сделать
   миграцию: колонку `ics_tokens.token_raw` (или `token_salt`) и убрать кэш?
   Компромисс указанного выше решения: сырой токен лежит в jsonb-кэше, т.е. выгрузка
   одной строки студента выдаёт корм-ссылку (без кэша выдала бы только хеш).
2. Кэш живёт до ежедневного сброса демо-данных: после него первый `GET /api/me/ics`
   создаёт НОВЫЙ токен (старый корм 404) — приемлемо ли для демо, или после reset
   ссылка должна «доживать» иначе?

## 4. Семантика корма

- Окно пар — ±4 недели (28 суток) от `now()` с обеих сторон, `[start, end)` по `startsAt`.
- Перенесённая пара — одно событие на новом месте; `cancelled` — событие с
  `STATUS:CANCELLED`; `added` — на новом времени (как `ScheduleDTO`).
- Дедлайны: только `starred = true`, **без окна** (подписка показывает и прошедшие/далёкие —
  окно в тикете оговорено только для пар). События `SUMMARY "Дедлайн: <title>"`,
  длительность 30 минут на момент `dueAt` (не all-day: мобильные календари по-разному
  показывают all-day из подписки, а точное время дедлайна полезно).
- SUMMARY пары — `"<shortTitle> (<type>)"` — формат из тикета; `type` остаётся
  машинным (`seminar` и т.п.): тексты интерфейса Claude может переопределить.
- UID: `class-<classes.id>@kompas`, `deadline-<deadlines.id>@kompas`.
- `dtstart`/`dtend` отдаются в UTC (`startInputType/OutputType utc`).
- Хедер: `X-WR-CALNAME: Компас` (через `calName`); `PRODID` библиотеки по умолчанию.

## 5. Нюансы реализации

- Лимит 60/час — `RateLimiterMemory` (points 60, duration 3600) **на токен**,
  состояние в памяти процесса: перезапуск сбрасывает (кратковременное окно
  мильд-перенасыщения после рестарта — accept, SPEC §9.7 про требование лимита).
  60 выключений до 429, `ROUTE_LIMITED`→ нет: код ошибки `RATE_LIMITED`.
- Публичный роут: поиск владельца — соединением владельца (как у `/api/verify`),
  пары/дедлайны — строго внутри `withUserTx` владельца; `findStudentContext` для группы.
- Токен в URL приходит сегментом с суффиксом `.ics`; без суффикса тоже принимается.
- `withIdempotency` на rotate НЕ применяется: повтор обязан выдать новый токен.
- Библиотека `ics@3.12.1`: экспортирует `createEvents` (sync) и `createEventsAsync`;
  `metadata` из упоминания тикета в этой версии нет, используется `calName`.

## Ответ Claude (ревью фазы B, 08.11.2026)

1. **Кэш сырого токена в `idempotency_keys` отклонён** — он сводил на нет хранение только хеша (выгрузка БД = все ссылки), и служебный ключ `ics-feed-url` совпадал с форматом клиентского Idempotency-Key. Сделано через миграцию `0002`: в `ics_tokens` появилась колонка `generation`; токен = `HMAC-SHA256(VERIFY_SECRET, "ics:" + userId + ":" + generation)` в base64url (43 символа). GET выводит ту же ссылку без хранения, rotate → `generation + 1`, старый токен 404. В БД — только хеш и номер поколения.
2. **Сброс демо-данных** теперь не меняет ссылку, если строка `ics_tokens` пережила сброс; если нет — первый GET создаёт поколение 1 (та же ссылка, что и до сброса при той же `generation`).
3. `url` относительный — **принято**.
4. Семантика корма — **принята**.
5. **Лимит исправлен:** сначала нормализация (`.ics`) и проверка формата `^[A-Za-z0-9_-]{43}$` (иначе 404 без расхода лимита), ключ лимитера — хеш токена. Мусорные сегменты больше не раздувают память лимитера.
