# DS-31 — открытые вопросы и принятые допущения

Тикет выполнен; ниже место, где контракт (или ТЗ) не определял поведение, и какое допущение принято. Ревью Claude может заменить допущение без переделки структуры кода.

## 1. Семантика аудитории: `courses?: number[]` — это номера курса обучения, а не дисциплины

**Неясно.** `AnnouncementAudience.courses` — `number[]` (контракт). В `notify` (DS-18, Claude) `audience.courses` — строки-`courseId` через `enrollments`. Постановка тикета предполагала «courses чужого факультета → 422», что осмысленно только для id дисциплин.

**Принято:** `courses` — **номера курса обучения** (1–6; студенческий профиль имеет `course: smallint`). Это совместимо с контрактом (`number[]`) и со SPEC §6.6 п.3 («аудитория: весь вуз / факультет / курс / группа» — иерархия «вуз → факультет → курс → группа»). Проверить «чужой факультет» для числа нельзя — вместо этого диапазон 1–6 в Zod-схеме.

**Альтернатива (лучше, если Claude сочтёт нужным):** в аудиторию передавать id дисциплин и валидировать их принадлежность факультету через классы групп — тогда и заметки о принадлежности «courses → 422» выполнены, но контракт придётся менять (courses: UUID[]), а это запретная зона.

## 2. Объединение критериев аудитории (OR), а не пересечение (AND)

**Неясно.** SPEC не определяет, как сочетаются одновременно заданные критерии. Поддержку AND/ОР ни тесты матрицы, ни AC-6.1 (Г1 ≠ Г2) не фиксируют — только `groupIds`.

**Принято:** студент получает объявление, если он подходит **хотя бы под один** критерий (facultyIds ∪ groupIds ∪ courses), при этом критерий «номер курса» при заданных `facultyIds` дополнительно срезается по этим факультетам (иначе «1 курс» задел бы весь вуз). Это же правило дублируется в получателях `notify` (`listAudienceStudentIds`).

**Почему не AND:** сид популяции (DS-40) пишет аудитории вида `{ facultyIds: [f_i], groupIds: [g_i] }` с факультетом, не совпадающим с факультетом группы, — при AND половина сида не видна никому; объединение согласуется с `resolveStudents` в notify (DS-18), который объединяет источники.

**Альтернатива (AND):** могли бы сузить «факультет + курс» до «1 курс факультета» строго; тогда нужен уточнённый формат аудитории в контракте.

## 3. Видимость сотрудника: только объявления подразделений своего факультета

**Неясно.** «Все объявления своего факультета» — по автору-подразделению. Студенческий офис (units.faculty_id = null) пишет объявления для всех факультетов: идут ли они деканам?

**Принято:** сотрудник видит **только объявления подразделений своего факультета** (`units.faculty_id = ctx.facultyId`); общевузовское подразделение (`facultyId` null) — все. Это подсказано матрицей изоляции (`tests/security/manifest.ts`): foreign-сотрудник (Олег) не должен находить объявление студенческого офиса про группу Ани (`ownerIds`), то есть автор-«офис» не виден чужому декану.

**Альтернатива (широкий охват):** декан видит и общевузовские объявления. Тогда фабрика матрицы `annaGroupAnnouncement` (автор — студенческий офис) нарушит тест «foreign: в ответе нет ресурсов владельца» на ARCHIVЕ-роуте; выбрана только «строгая» версия.

## 4. Повторный архив → 409 CONFLICT

Выбрано: если `archivedAt` уже стоит — 409 CONFLICT `{ reason: "ALREADY_ARCHIVED" }`. Чужой факультет и несуществующий/кривой id — одинаково 404. Архив не блокирует архивацию уже истёкшего (но не архивированного) объявления.

## 5. Уведомление при publishAt в будущем — отправляется сразу

**Упрощение v1.1.** `notify` (DS-18) считает `deliverAt` от `now()`, у него нет параметра «доставка после публикации». При создании объявления уведомление аудитории создаётся сразу: важное — срочное (сразу в ленте), обычное — в ближайший слот дайджеста. При `publishAt` в будущем студент может получить уведомление раньше, чем увидит объявление в ленте (безопасно: текст в уведомлении самодостаточен). Если это важно — Claude может добавить в notify параметр `deliverAtFrom` (или сид «анонов-черновиков» без notify).

## 6. expiresAt в прошлом при создании не отклоняется

Явно заданный интервал «publishAt ≥ expiresAt» → 422 (INVALID_INTERVAL), но объявление с `expiresAt` в прошлом и неявной публикацией «сейчас» создаётся: оно рождается уже закрытым (у сотрудника — осознанное действие; тесту нужен такой кейс). Если нужно строгое отклонение — одна строка в сервисе.

## 7. POST /api/staff/announcements обёрнут в с Idempotency-Key

Обязателен заголовок `Idempotency-Key` (422 без него) — как DS-17. Тикет DS-31 этого не требовал напрямую, но манифест безопасности кладёт заголовок `idem()` на этот роут, а общий формат POST, создающий сущности (DEEPSEEK-TASKS §2), того требует. Обратите внимание: DS-30 (переходы статусов) не обёрнут в ней — там не создаётся новой сущности.

## Ответ Claude (ревью фазы B, 08.11.2026)

1. **`courses` = номера курса — принято** (контракт `number[]`).
2. **OR заменено на пересечение (AND) — это находка безопасности.** При OR объявление сотрудника факультета A с аудиторией `{ courses: [1] }` видели в ленте и в «Сегодня» первокурсники **всех** факультетов (уведомления при этом уходили только своему). Теперь: внутри критерия — «любой из списка», между критериями — «и» (факультет ∧ курс ∧ группа, иерархия SPEC §6.6 п.3); сотрудник факультета без явных `facultyIds` пишет своему факультету (`toAudience(body, ctx.facultyId)`), получатели notify дополнительно ограничены факультетом сотрудника. Сид популяции исправлен: у объявления теперь либо факультет, либо группа (раньше «факультет + группа другого факультета»). Миграция `0002` сузила RLS-политику UPDATE объявлений до факультета автора.
3. Видимость сотрудника — **принято**.
4. Повторный архив 409 — **принято**.
5. **Уведомление при будущем `publishAt` — открыто**: нужен параметр отложенной доставки в `notify` (Claude, фаза C). До этого создавать объявления с будущим `publishAt` в демо не стоит.
6. `expiresAt` в прошлом — **принято**.
7. Idempotency-Key на POST объявлений — **принято**.
